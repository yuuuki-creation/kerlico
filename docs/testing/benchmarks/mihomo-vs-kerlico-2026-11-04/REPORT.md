## 二、测试环境与方法

- **硬件与系统**：
  - `perf-01`（客户端 / 内网环回主机）：Intel Xeon Platinum 8269CY @ 2.50GHz（8 逻辑核，AES-NI / AVX2 / AVX-512），12 GiB 内存，Debian 13 (`x86_64`, Linux `6.12.41+deb13-amd64`)。
  - `perf-03`（公网跨机服务端）：AMD EPYC 7R13（8 逻辑核，AES-NI / AVX2 / VAES / SHA-NI），8 GiB 内存，Debian 13 (`x86_64`, Linux `6.12.115+deb13.1-amd64`)。
- **测试模型（`tools/bench_vs_mihomo.py`）**：
  - **对比拓扑**：`mihomo` 同时具备客户端与服务端实现的 58 个组合采用 `dual_end`（`kerlico C + kerlico S` 对标 `mihomo C + mihomo S`）；`mihomo` 仅具备客户端实现的 12 个组合（`vless/xhttp-h2-tls`、`vless/xhttp-h3-tls`、`snell/*`、`wireguard/udp-l3`、`hysteria1/*`、`shadowsocksr/*`、`ss2022/*-eih`）采用 `client_vs_kserver`（固定 `kerlico S`，对比 `kerlico C` 与 `mihomo C`）。
  - **工作负载**：
    - 公网跨机（`--duration 30`）：单流（`1S`）与 8 并发流（`8S`）各持续满载传输 30 秒，统计有效业务吞吐（`MiB/s`）、双端峰值常驻内存（`Peak RSS`）与每 MiB 业务流量的双端总 CPU 耗时（`CPU-ms/MiB`）。
    - 内网环回：单流固定传输 `64 MiB`、8 并发流固定传输 `256 MiB`（`8 x 32 MiB`）。

## 五、关键数据面优化总结

1. **通用转发、TLS 与多路复用底座（`crates/core-api`、`crates/net`、`third_party/xray-transport`）**：
   - 将双向转发缓冲区 `DEFAULT_RELAY_BUFFER_SIZE` 扩至 `256 KiB`，消除长肥管道（高 BDP 公网）下的小块读唤醒。
   - `sing-mux`（`smux`/`yamux`/`h2mux`）引入 `64 KiB` `BufReader`、`48 KiB` 写帧聚批与 `poll_reserve` 背压许可，避免多流并发下的小帧系统调用风暴与入站流映射泄漏。
   - WebSocket、HTTPUpgrade 与 XHTTP/H2 载体移除每次帧解析的冗余零初始化分配，改为预留容量与向量化批量写出。
2. **AEAD 流协议零清零读取与满帧写出（`vmess`、`vless`、`trojan`、`shadowsocks`、`ss2022`、`shadowsocksr`、`snell`）**：
   - 借助 `tokio::io::ReadBuf` 未初始化切片直接承接底层 socket 读取，消除每帧 `16 KiB`–`64 KiB` 的用户态内存清零开销。
   - `Shadowsocks` 与 `SS2022` 写帧上限提升至协议允许的最大载荷（`0x3FFF` / `0xFFFF`），`Snell` 扩至 `32 KiB` 原地加解密缓冲，`ShadowsocksR` 实现 `tls1.2_ticket_auth` `64 KiB` 帧聚批并移除逐分片强制 `flush()`。
   - `VLESS` REALITY 与 XTLS Vision 读写状态机改用预分配连续缓冲区与批量 TLS 记录处理，公网 8 流吞吐分别达到 `mihomo` 的 `101.4%` 与 `142.3%`。
3. **QUIC 与自定义 UDP/TCP 传输协议（`hysteria1`、`hysteria2`、`tuic`、`trusttunnel`、`mieru`、`wireguard`）**：
   - `Hysteria1`、`Hysteria2`、`TUIC` 与 `TrustTunnel H3` 统一将底层 UDP 套接字收发缓冲区扩至 `4 MiB`–`8 MiB`，并将 QUIC 流/连接级接收窗口提升至 `16 MiB`–`64 MiB`，在高丢包与高延迟公网路径上充分填满带宽时延积。
   - `Mieru` 用单向 `SimplexStream` 替代双向 `DuplexStream`，配合 `64 KiB` `BufReader`、写端批量聚合及无锁原子 UDP 序号分配，公网 `tcp-mux` 吞吐达 `mihomo` 的 `224.6%`，`tcp-nomux` 峰值内存仅为 `mihomo` 的 `14.3%`（`151.6 MiB vs 1060.3 MiB`）。
   - `WireGuard` 用户态 `smoltcp` 栈将 TCP 套接字缓冲区扩至 `2 MiB` 并支持单次轮询连续收发突发报文，公网与内网吞吐分别达到 `mihomo` 的 `94.8%` 与 `113.3%`。
4. **计算密集型与帧复用协议（`sudoku`、`anytls`）**：
   - `Sudoku` 编码层预计算平坦化 `wire_clues`、`raw_hint_index`/`raw_group_index` 查找表与内联 `FastRng`，并对 `32 KiB` 以上负载启用 `ParallelRecordStream` 双线程分段并行编解码；HTTP 分离传输（`stream`/`poll`）在 `h1_compat.rs` 实现 `ReadBuf` 零拷贝直通、在 `pull.rs` 按模式分档聚批（`stream` `64 KiB`、`poll` `32 KiB`）并采用非阻塞 `SplitIo::poll_flush`，使内网 6 个组合全部跃升至 `82.0%`–`95.0%`，公网 `stream`/`poll` 吞吐达 `mihomo` 的 `3.77x` 与 `2.71x`。
   - `AnyTLS` 移除每条逻辑流的 `256 KiB` `DuplexStream` 中转任务，改为 `LogicalStream` 直接持有 `PollSender<QueuedFrame>` 并在 `poll_read` 中一次合并消费多帧，底层 TLS 读端外包 `128 KiB` `BufReader` 并由 `LogicalStream::drop` 唯一管理活跃流计数，内网 8 流吞吐提升至 `694.97 MiB/s`（`mihomo` 的 `86.1%`）。
