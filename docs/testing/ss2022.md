# Shadowsocks 2022 验证记录

日期：2026-10-30。对应 P-04、K-S2。本轮三算法双端 TCP/原生 UDP、AES 终端 EIH 多用户及客户端身份链已完成包级验证和下述固定对端互通；测试范围和对端限制分别记录。

## 环境与原语

- worker：`perf-01` 独立项目目录，Linux x86_64，`rustc 1.99.1 (58cf8f9c3 2026-10-13)`、`cargo 1.99.1 (5f94df478 2026-08-27)`，`CARGO_BUILD_JOBS=1`。
- 协议原语：`shadowsocks =1.25.0`，VCS `ab388c7466d21f979430e33cc9ef10e22fb05955`；实际解析的密码依赖和许可证见[研究记录](../../reference/research_notes/ss2022-implementation.md)。
- 对端：sing-box v1.14.4、Xray v26.10.29，下载到本任务工作区，下载内容与官方 GitHub release API 的 SHA256 digest 一致，运行时再次核对版本；未安装到系统路径。
- 本地只编辑、阅读、同步和管理仓库。格式、构建、Clippy、Python 语法检查、测试及代理运行均在 worker 执行；没有更改既有基础服务。

## 包级检查

最终任务 `final-r2` 返回 `0`：

```sh
cargo fmt -p kerlico-ss2022
cargo test -p kerlico-ss2022 --all-targets
cargo clippy -p kerlico-ss2022 --all-targets -- -D warnings
cargo fmt -p kerlico-ss2022 --check
cargo build -p kerlico-ss2022 --example peer
python3 -m py_compile tools/interop_ss2022.py tools/interop_ss2022_chain.py
```

Rust 共 8 项测试通过：1 项窗口单元测试、1 项预算/取消集成测试、6 项协议集成测试。协议测试内逐算法、逐单用户/EIH 模式循环，不能将 8 项解释为仅 8 种线上组合。

| 检查 | 实际覆盖 |
| --- | --- |
| 三算法自互通 | 双端 TCP、原生 UDP；TCP 100000 字节并验证半关闭后反向读取至 EOF；UDP 空包、短包、64000 字节及 65001 字节主动拒绝 |
| EIH | AES-128/AES-256 终端用户鉴权、两名用户使用相同 client session ID 的隔离 |
| 认证/配置 | 三算法错误 TCP key 不打开目标；UDP AEAD 篡改包丢弃且不推进窗口；错误 key 编码、未知字段、重复 key、ChaCha identity/多用户拒绝 |
| UDP 状态 | 回放拒绝、乱序和过旧包、源端口迁移、同 session 多目标、目标首次失败后的新包恢复且不重放旧包 |
| 资源/取消 | 会话消耗预算后目标预算不足时不打开出口；节点取消归还全局/节点名额并记录完成事件 |

这些包测试注入实现 `AccessService` 的内存 echo，代理 TCP/UDP 载体实际使用回环 socket。IPv4/IPv6/域名目标编解码与服务调用因此有覆盖，但实际业务目标网络连接以后一节的对端实测为准。

## 固定对端矩阵

互通使用 `examples/peer.rs`，直接复用正式协议对象和核心契约；业务目标通过测试专用 `AccessService` 连接真实 TCP/UDP echo。测试程序仅为 worker 验证辅助，不是另一个发布内核，也没有把外部代理进程接入产品数据路径。

每个下表组合都分别运行 Rust 客户端与 Rust 服务端，分别连接 IPv4 `127.0.0.1` 和 IPv6 `::1` 业务目标。SS2022 监听和代理载体使用 IPv4 回环。TCP 负载为 131072 字节；UDP 每场景发送 6 字节和表中较大负载。

| 模式 | sing-box v1.14.4 | Xray v26.10.29 |
| --- | --- | --- |
| AES-128-GCM 单用户 | 双角色、双目标族 TCP/UDP 通过；UDP 8192 字节 | 双角色、双目标族 TCP/UDP 通过；UDP 4096 字节 |
| AES-256-GCM 单用户 | 同上 | 同上 |
| ChaCha20-Poly1305 单用户 | 同上 | 同上 |
| AES-128-GCM 终端 EIH | 同上 | 同上 |
| AES-256-GCM 终端 EIH | 同上 | 同上 |

sing-box 的最终 `sing-final` 为 20 场景、20 项 TCP 和 20 项 UDP 通过；Xray 的 `xray-final` 同样为 20 场景、40 项通过。这里一项 UDP 包含两种负载，未重复累计为多个组合。

另以 `Rust 客户端 → Xray relay → Rust EIH 终端 → echo` 验证两层身份链：两种 AES、两种目标地址族共 4 场景、8 项 TCP/UDP 全部通过，UDP 为 6/4096 字节。该结果验证本模块的客户端链编码和终端，不表示本模块实现了 relay 服务端，也不外推所有八层链部署。

## 已保留的失败与修正

1. 首次格式检查发现格式差异，仅在 worker 格式化后取回。首轮测试通过，但 Clippy 拒绝未处理空写长度和已弃用的原子 API；集中修正后完整复验通过。最终依赖从候选 1.24.0 更新到已重新研究的 1.25.0，最终结果均针对后者。
2. 首次 Xray 服务端 TCP 超时。调试日志显示握手/目标解码成功，`freedom` 的默认私网规则将回环 echo 黑洞；测试配置改为只精确放行该回环目标和随机端口，TCP 全矩阵复验通过。没有修改系统或已有代理配置。
3. Xray `xray-full-r2` 的 20 场景 TCP 全部通过，但 8192 字节 UDP 业务负载全部超时，6 字节包已先通过。固定 [SS2022 UDPReader](https://github.com/XTLS/Xray-core/blob/0afec66085a85191e9dd2a4a6646c7c9a94688d1/proxy/shadowsocks_2022/packet.go) 使用 `buf.New().ReadFrom()` 接完整密文，而 [Buffer.Size](https://github.com/XTLS/Xray-core/blob/0afec66085a85191e9dd2a4a6646c7c9a94688d1/common/buf/buffer.go) 为 8192；业务负载加协议头后超过该缓冲区，与现象一致。此处不声称已经精确测得所有方向的最大可用负载。4096 字节已独立复验通过；8192 字节失败未删除，也未通过非标准分片掩盖。
4. 静态复核发现关闭目标的旧 sender 会持续丢弃同 session 后续新包。已改为在保留会话及回放状态的同时，让通过窗口的新包重建目标；增加失败后恢复测试，并重新执行最终包检查与完整正向矩阵。

原始日志、逐场景 JSON、发行 digest、工具链信息及同步状态只保存在本地私有测试目录；可提交记录不含连接凭据或真实机器信息。

## 验证边界

根程序/engine 的 IPv4/IPv6 独立节点装配、跨节点实际凭据拒绝和域名 IPv4 优先已在下一节补正式 CLI 集成。前面的包级和 peer 对端矩阵单独看仍不替代这些证据。

本模块不提供 relay 服务端、SIP003、UoT 或通用 mux；ChaCha EIH 属非法配置。没有进行吞吐/压测、长期运行、多平台原生验证或最低 Rust 版本实测。

## 正式 CLI 集成补充

perf-01 的 `cli-r1` 返回 `0`，17 组正式 CLI 集成检查全部通过。根程序的 `protocol-ss2022`/`ss2022` feature 和双端工厂使用实际装配代码，共享文件未作修改。

本轮只构建以下两份程序，并分别保留二进制，没有构建默认协议集合或运行 workspace 全量测试：

```sh

cargo build -p kerlico --no-default-features
```

使用独立 target 目录、`CARGO_BUILD_JOBS=1`、`CARGO_PROFILE_DEV_DEBUG=0`、关闭增量编译，并降低自身构建进程优先级。没有改变宿主工具链或其他服务。

`tools/interop_ss2022_cli.py` 实际启动正式 CLI；`examples/cli_probe.rs` 作为原生客户端探针，直接向正式节点发送 SS2022 包。正式客户端数据路径则由同一 CLI 进程中的固定转发入口、正式 `Ss2022Outbound` 和节点共同运行；没有用 probe 或先前的 peer 程序替代该路径。

| 检查组 | 实际结果 |
| --- | --- |
| 模块/配置剪裁 | SS2022 构建只列出 direct/reject 出站及 SS2022 双角色；无协议构建只列 direct/reject，接受直连配置，分别拒绝 SS2022 出站和节点配置 |
| 配置边界 | 重复服务 key、跨节点重复用户 key、IPv4-mapped IPv6 监听、与节点冲突的 UDP 转发监听均被拒绝；三算法节点配置接受；目标端口已占用时 `check` 仍通过，未绑定监听 |
| 同进程双角色 | 使用两个独立 key 的 IPv4/IPv6 节点；每节点 TCP/UDP 同端口；各自访问真实 IPv4、IPv6 echo，共 4 条 TCP 和 4 条 UDP 路径通过。TCP 同时验证目标先发数据与半关闭后的 EOF |
| 凭据运行时隔离 | IPv4 节点使用 IPv6 节点 key，以及反向使用，TCP/UDP 都未获得目标数据；目标侧也没有收到错误凭据所携负载 |
| 统一目标访问 | 客户端固定转发请求 `localhost` 的 TCP/UDP 都选择 IPv4；原生探针另向两种节点发送 `localhost` 目标，TCP/UDP 也都选择 IPv4。探针先确认系统候选同时存在两类地址，双栈 echo 用不同前缀区分实际命中地址族 |
| 正式节点原生 UDP | 两种节点均通过相同 session 的 IPv4/IPv6 多目标、源端口迁移、回放拒绝；同 session 的 server session ID 保持一致。目标侧计数确认回放未再次出站 |
| IPv6 wildcard | 正式 `::` 节点的 IPv6 TCP/UDP 均可鉴权并访问 IPv4 echo；IPv4 TCP 连接被拒绝，使用正确 key 的 IPv4 UDP 包也未进入目标，验证两种 socket 的 v6only 边界 |
| 节点预算 | 单节点两份名额由 UDP session 与首个目标占满后，新目标、新 session 和同节点 TCP 均受限；另一节点 TCP 仍成功，原有目标仍可继续交换数据 |
| 全局预算 | 两份全局名额被首节点 UDP session 与目标占满后，另一节点 TCP 同样受限；原有目标继续工作，受限负载没有进入 echo |
| 排空与重启 | 带活跃 UDP session/目标的正式进程收到 SIGTERM，配置排空预算为 500 毫秒，在集成检查上限 2 秒内以状态 0 退出；原配置同端口随即重启和退出成功。节点预算与全局预算两种场景分别执行 |

17 是脚本中的分组记录数，不是将每个地址族、传输和断言分别累计的检查总数。本轮根运行路径选用 AES-128-GCM 单用户；其余算法和 EIH 的线上组合证据仍以前述包级及固定对端矩阵为准，不机械重复。

集成日志、17 组 JSON 结果、验证时共享源码及两份二进制的 SHA256、对应 Cargo.lock 副本只保存在私有目录。共享源码后续发生变化时，应复验实际受影响路径。本轮未发现需要提交共享代码补丁的问题。
