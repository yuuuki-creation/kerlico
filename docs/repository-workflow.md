# 文档、状态、决策与参考资料约定

更新日期：2026-10-30，Asia/Shanghai。本文是当前仓库维护方式；架构技术选择仍按其各自状态记录，维护本文不代表开始实现。

## 存放位置与唯一职责

全部先用仓库内的 Markdown 保存，可以本地阅读、检查和以后随 Git 版本维护。当前不引入外部知识库、自动生成脚本或另一套状态数据库。

| 位置 | 保存什么 | 维护边界 |
| --- | --- | --- |
| 根 `README.md` | 项目介绍和阅读入口 | 保持简短，不重复维护详细进度和完整设计 |
| 根 `AGENTS.md` | 协作规则、工作阶段和授权边界 | 不充当设计全文、待办清单或聊天日志 |
| 根 `.gitconfig`、`.githooks/` | 固定匿名身份与仓库管理校验 | 仓库级生效，不修改全局身份，不作为 VPN 实现 |
| 根 `STATUS.md` | 当前阶段、已完成资料/功能、待决项、下一步和验证状态 | 项目进度的统一入口；明确区分文档完成与功能完成 |
| `docs/README.md` | 本项目设计导航 | 不另建一份独立的进度表 |
| `docs/*.md` | 本项目当前设计、行为契约和模块责任 | 一个主题一处维护；引用上游依据时链接借鉴条目 |
| `docs/decisions/` | 重要选择的原因、取舍和确认状态 | 记录为什么作此选择；按编号保留已确认选择的演变 |
| `reference/README.md` | 上游资料导航、固定版本与来源边界 | 上游基线的统一入口，不表示本项目采用了其所有能力 |
| `reference/research_notes/`、`reports/` | 已查阅的证据、调研分析和横向报告 | 现有资料保留路径，固定快照不能静默改写成 latest |
| `reference/design-map.md` | 上游证据 → Rust 设计建议 → 验证目标 | 区分借鉴、已采纳和已验证，不把研究推论变成事实 |
| `reference/.upstream/` | 未来按需下载的上游只读源码缓存 | 不提交、不作为本项目实现或构建依赖；当前未下载 |

`STATUS.md` 中的项目状态与内核运行时状态是两类数据。未来的连接、健康、流量和配置代次通过内存状态及控制接口呈现；需要持久化的缓存、映射和运行记录归运行数据目录，具体路径随平台/宿主确定，不写进仓库的 STATUS 或 docs。

## 更新方式

开始工作先读 `AGENTS.md`、`STATUS.md` 和相关设计文档。完成一项有实际结果的工作后，更新受影响设计和状态摘要；没有新进展时不为了刷新日期反复改文件。

新写或实质修改的设计文档注明草案/已确认/已取代状态、日期，并在适用时链接关联决策和借鉴依据。设计正文描述当前方案，变更原因交给决策记录，避免不断向正文追加过时方案。

一个结果只在一个主位置维护：进度在 STATUS，设计在相应主题，决策理由在 decisions，上游事实在 reference。其他位置链接或概括，不另造相互独立的版本。聊天中的建议未被确认时保持草案；用户认可讨论不自动授权开始编码。

STATUS 保留当前摘要和少量关键变化，不记录每次工具调用或聊天全文。Git 历史保存文档变化，但维护文档不自动授权创建提交或推送。用户新增了[强制匿名要求](anonymity.md)，本地 Git 配置和校验钩子用于落实该要求，不改变当前未开始 VPN 实现的阶段。

## 重要选择怎样保存

采用简短决策记录，规则见 [decisions/README.md](decisions/README.md)。每份回答：问题、约束、备选、建议与代价、确认状态、影响范围、参考依据和验证目标。

普通文字修正、链接维护和文件说明不需要创建决策记录。workspace 组织、异步运行时、首批平台、协议模型、配置兼容与更新语义等会长期影响设计的选择才值得记录。草案可以先写；只有用户明确确认后才登记为已确认。

## 怎样借鉴三个上游

先提出本项目要解决的行为问题，再查固定版本的源码和文档。按现有调研，优先从 mihomo 追元数据、策略/provider、UDP 与映射，从 sing-box 追组件注册、装配与宿主边界，从 Xray 追 Dispatcher 和协议/传输/安全分层。详细出处及局限见[借鉴映射](../reference/design-map.md)。这只是阅读分工，不是确定某个项目为整体模板。

每项借鉴按以下顺序落盘：

1. **问题**：本项目需要满足什么行为，相关产品范围是什么。
2. **证据**：上游仓库、标签、完整 SHA、具体文件/行和观察结论；动态网页另注访问日期和版本。
3. **取舍**：比较相关项目的处理方式，写清适用范围与未验证点，不用协议数量或主观性能排名代替理由。
4. **Rust 设计**：按所有权、异步取消、流/包边界、资源清理和可选依赖重新表达；不机械翻译 Go 的全局状态、反射或 goroutine 结构。
5. **落点**：在借鉴映射中链接到本项目设计；重要选择形成草案决策，确认后同步设计和 STATUS。
6. **验证**：先记录互通、异常、生命周期与平台验收目标；获得实现指令后才写实现和测试，完成后再登记验证结果。

“上游存在该功能”“我们建议借鉴”“我们已决定采用”“实现完成”“验证通过”必须分别记录。尤其不能从控制 API 推出无损热更新，从入口映射推出完整 NAT 等价，或从某平台的源码推出所有平台均已可用。

## 上游源码放哪里

当前可通过现有固定源码链接阅读，不要求把三个仓库全部提交进本项目。需要本地深入跟踪时，按需放在 `reference/.upstream/<project>/<sha>/`，保留其来源和许可证文件，以固定提交只读查阅。

缓存目录由根 `.gitignore` 排除；基线信息仍在 `reference/README.md` 记录。设计与决策必须引用稳定远端链接，不能只链接某台机器的缓存路径。删除缓存不应丢失调研结论，也不能影响本项目构建。

本项目默认借鉴行为、边界和工程经验。以后若决定复制、移植代码或采用具体依赖，需要另记准确来源、提交、使用范围及对应许可证/署名要求；仅将实现语言改为 Rust 不能替代来源记录。本轮不决定项目许可证或代码复用方式。
