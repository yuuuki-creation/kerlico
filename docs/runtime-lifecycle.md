# 运行、配置更新与资源生命周期

状态：本轮架构建议，2026-10-30。这里定义预期状态与失败边界，不承诺当前已有在线更新或无中断能力。[核心契约](core-contracts.md)与[数据路径](data-paths.md)使用相同的标识和所有权概念。

## engine 状态与健康状态分开

| 运行状态 | 可进行的动作 | 退出条件 |
| --- | --- | --- |
| Created | 注册工厂、解析和校验配置 | 有效装配计划产生，或失败后结束 |
| Preparing | 构造候选实例、取得允许准备的资源 | 所需依赖就绪；不能提前对外接受业务 |
| Starting | 按计划启动资源和服务，完成平台操作 | 全部必需部分就绪后打开接入闸门 |
| Running | 接纳会话、处理控制请求和受支持的更新 | 停止请求或不可继续的运行故障 |
| Quiescing | 停止新接入及新的独立工作，通知会话准备结束 | 所有入口停止产生新会话 |
| Draining | 允许已有转发在预算内结束 | 所有会话结束，或达到统一排空截止时间 |
| Stopping | 取消残留任务、回收资源并恢复平台状态 | 完成清理，或记录无法清理的资源与原因 |
| Stopped | 只读最终结果 | 不允许旧句柄重新提交工作 |

任何启动失败都进入清理路径，不能把“构造返回错误”视为外部资源已经自动恢复。运行状态之外单独记录健康与最终原因，例如正常停止、启动失败或关键服务失败；避免一个 Failed 状态同时表示“正在清理”和“已经清理”。

同一个控制请求重复停止应具有幂等效果；并发启动、停止、配置发布和平台变更由单一控制序列协调。控制序列只调度操作，不把整个网络等待放在全局锁内。

## 构造、准备与激活

1. **Decode / Validate**：解析文件、解码协议选项、检查标识/能力/引用和依赖环。可以读取明确输入资料；不绑定监听器、创建 TUN、拨号或修改系统网络。
2. **Plan**：生成实例依赖图与资源操作计划。对比现状，分类为可共享、可新建、需要受控替换或需要重启；列出对应的清理责任。
3. **Prepare**：按依赖顺序构造候选实例并准备允许暂存的资源。网络准备及句柄获取可能有副作用，必须被追踪；不能把此阶段宣传为纯校验。
4. **Activate**：按平台步骤完成资源就绪，必需服务确认可用后打开接入闸门。出站与解析等依赖先于使用它们的入口就绪。
5. **Cleanup on failure**：以资源获得的逆依赖顺序停止和释放，记录每个操作的成功、失败和待宿主处理状态。原有资源只能在所有者确认允许时被释放。

依赖图描述运行服务，不仅是 crate 引用。例如代理服务器的引导解析、DNS 的出站、选择组的候选集合都要显式进入校验。动态资源在运行中引入的关系还需有限访问链检查，启动时拓扑排序不能代替所有运行时防环。

## 配置代次与既有会话

成功发布产生一个新的 `ConfigGeneration`，包含只读配置、路由与服务引用。入口在**接纳会话时**固定代次，鉴权、元数据和后续建立不能中途各取一次“最新配置”。共享监听器也要先选择一个代次绑定，再开始该代次的协议处理。

推荐普通更新采用以下行为：

| 对象 | 代次行为 |
| --- | --- |
| 新接纳的根会话（TCP 或独立 UDP 关联） | 使用发布后接纳到的代次 |
| 由既有控制会话建立的 UDP 关联 | 继承父会话的配置与认证绑定，不在派生时重新取最新配置 |
| 既有 TCP 会话 | 保持已选出站与必要资源，不因规则变化重新拨号 |
| 既有 UDP 关联及其目标流 | 继续使用关联固定的代次；派生查询和新目标也继承它，直到关联结束或被显式排空 |
| 已建立连接的健康观测 | 可以更新观测数据，不据此自动把业务字节迁往其他节点 |
| DNS 与规则快照 | 子查询继承调用者代次；缓存仅在语义兼容时复用 |
| Fake-IP 映射与独占设备 | 独立管理资源使用期，不随旧配置对象一起直接销毁 |

这意味着普通规则更新不等于立即撤销所有旧会话。若要求撤权或强制切换，需要显式操作、受影响会话集合和可观察结果，不能用看似普通的配置发布偷偷中断连接。

会话只保留实际需要的依赖闭包，不必固定整个 engine 对象。UDP 关联若还可以建立新目标，其旧路由、解析与出站集合也属于必要闭包，不能过早清理。资源 lease 不自动解决资源退出：仍需停止新使用、跟踪使用者并在截止时间后按策略取消。

连续更新可能积累旧代次，因此要限制保留代次数、旧关联最大使用期和排空预算。达到限制时，更新应返回需要排空/重启的结果，或执行用户已经选择的排空策略，不能无限保留旧配置，也不能无声地删除被引用资源。

## 在线更新按能力开放

建议第一版先实现一致的启动与停止，**未声明支持的更新返回 RequiresRestart**。之后按下表逐项支持并验证；表中“可替换”是目标行为，不代表当前已有此功能。

| 变更 | 推荐目标行为 | 必须检验的边界 |
| --- | --- | --- |
| 规则与规则集 | 新根会话使用新快照，已有会话保留旧决策 | 规则格式、地址空间与已保留代次限制 |
| 选择组的新会话策略 | 发布新选择视图，不搬迁已建连接 | 候选引用有效、能力相容、观测与配置版本分开 |
| 节点地址或认证配置 | 构造新实例供新会话使用，旧实例排空 | 隐含连接池、复用通道和子任务是否可独立存在 |
| 监听地址、端口或接入鉴权 | 资源与接入绑定变化，默认按需重启 | 端口冲突、旧认证过程、监听器能否安全共享或切换 |
| TUN、MTU、系统路由或系统 DNS | 默认重启或宿主专门应用 | 独占、网络中断、系统恢复与权限行为 |
| Fake-IP 池或存储语义 | 专门迁移或重启 | 活动映射、TTL 宽限、地址冲突与持久化 |
| async runtime、栈后端、构建能力 | 重新构建或重启 | 不通过实例配置伪装成已支持的在线替换 |

规则数据更新和节点资源提供器可以复用“校验、准备、发布、退役”的流程，但数据格式正确不代表引用和能力一定满足。来源更新失败时保留最近有效版本，并记录失败；不发布半份集合。

### 一次受支持更新的顺序

1. 为请求分配操作标识并记录期望的当前代次。串行化发布或在提交前比较代次，防止旧请求覆盖后来的结果。
2. 校验并构造候选计划，分类每项变更。出现不支持的变更时返回明确结果，不自动重启 engine。
3. 准备全部新增依赖；失败时清理候选资源，当前代次继续服务。
4. 对受支持且已经就绪的对象，在接入选择点一次发布新快照；记录操作成功与新代次。这个发布点只保证进程内快照可见性，不是对 OS 网络操作的全局事务承诺。
5. 将旧代次标为不再接纳新的根会话，既有会话和其受支持的派生工作继续使用所需旧资源。依照上限和截止时间逐步退役。

平台改变不能用一次内存指针替换回滚。以后若支持此类更新，必须声明不可逆阶段、补偿动作与失败后的实际状态；补偿失败时可降级或停止，并把需要宿主处理的内容交给控制结果，不能报告“已恢复”却留下未知系统状态。

## 资源所有者与使用者

| 资源 | 唯一所有者 | 使用者如何持有 | 释放条件 |
| --- | --- | --- | --- |
| TCP/UDP 监听端点 | 监听资源管理对象 | 入站绑定与接入任务持有 lease | 停止接入、任务结束且无有效绑定 |
| TUN 设备与队列 | platform/宿主约定的资源对象 | tun 栈与收发任务持有明确句柄权限 | 任务停止后按接管/复制/借用模式释放 |
| 系统路由、DNS 与防回环设置 | 平台操作所有者 | 可核对的操作记录和资源标识 | 在应恢复时撤销本实例拥有的变更 |
| 出站连接池或复用连接 | 对应出站实例 | 会话持有租约 | 不再接纳新用户且现有用户结束或超时 |
| Fake-IP 存储 | 映射服务 | DNS 和会话持有映射引用 | 无活动引用并满足缓存/回收宽限 |
| 包队列与缓冲池 | 会话或受限共享池 | 单一所有权转移或明确共享引用 | 消费、整包丢弃、取消和排空均归还一次 |

不能为新代次盲目重开同一个独占设备或重复绑定同一监听地址。资源能否共享要比较语义与所有权，不只比较一个标签或数值 FD。新实例需要未支持的共享模式时，应在准备前判定需要重启。

宿主提供 FD 时，接口明确声明借用、复制或移交。仅有一个整数不能表达所有权；复制也不代表获得独立的设备或可独立撤销系统路由。恢复系统状态前核对变更是否仍归本实例所有，避免覆盖用户或其他程序后来做出的调整。

进程崩溃、强制终止和断电不保证执行正常退出。操作记录可辅助后续检查与恢复，但不能承诺任何异常下系统网络都会自动复原。

## 任务、取消与背压

每个长期任务归属 engine、实例、会话或资源作用域，并由其所有者追踪结果。只跟踪一个等待 Future 不足以证明底层工作已取消；Future 可能只是在等待另一个独立任务的结果。依据：[Rust Future 的运行特性](https://doc.rust-lang.org/std/future/trait.Future.html#runtime-characteristics)。

父作用域停止时通知子任务，给出统一截止时间，再等待退出或执行明确的强制清理。不要遗留无人持有的拨号、DNS、健康检查和 provider 更新任务。阻塞平台调用及重计算任务应有单独的受限执行安排；取消等待并不能保证已经开始的系统调用立刻撤销。

engine 退出时停止新的根会话和新的独立后台工作；已有 TCP 转发和已存在的 UDP 目标流在预算内排空。与普通代次退役不同，整机 Quiescing 后不再为旧关联启动新的目标流；剩余查询/握手按停止策略完成或取消。

连接数、关联数、流数、并发建立、队列包数/字节数和后台任务都有上限。大队列不能只限制包数而忽略字节数。锁用于短暂修改索引或状态，不跨网络等待；完成网络操作后还需核对资源/代次是否仍接受结果。

建议关闭分为显式的等待式关闭和最后的同步资源保护。标准 `Drop` 用于作用域释放和资源兜底，不用它代替需要等待网络任务完成的整个关闭流程。依据：[Rust Drop](https://doc.rust-lang.org/std/ops/trait.Drop.html)。任务 panic 与普通会话错误分别报告；关键收发任务失效时停止受影响入口或 engine，模块化本身不提供故障沙箱。

## 控制接口与操作结果

control 通过 engine 的控制端口提交请求，只读状态也从整理后的视图获取。建议变更请求统一返回操作标识、原代次、目标代次、阶段和结果；异步接收请求与更新真正生效分开显示。

结果应区分成功、配置无效、能力缺失、需要重启、已取消、准备失败和平台部分失败。查询更新结果可以幂等重试，重试不能重复创建资源。具体控制协议、远程暴露方式、访问控制和默认监听行为尚未决定。

## 未来验收场景

| 场景 | 要验证的目标 |
| --- | --- |
| 构造中途失败或部分服务启动失败 | 所有已获得资源有清理结果，不留下接纳业务的半启动实例 |
| 更新期间有鉴权、DNS、拨号在进行 | 每条会话使用一致代次，迟到任务不能覆盖新状态 |
| 连续发布且有长寿命 UDP 关联 | 旧资源与代次数有界，超限行为可观察 |
| 更新规则但不更新设备 | 新接入使用新快照，TUN 和有效 Fake-IP 映射保持正确所有权 |
| 变更监听器、TUN 或系统 DNS | 未支持的变更在准备前明确要求重启；不假装无损更新 |
| 关闭时对端不结束、任务不响应 | 统一截止时间生效，剩余任务与资源有明确结果 |
| 重复停止或重复查询操作结果 | 不双重关闭 FD、不重复撤销系统设置、不重复执行更新 |

本轮不实现上述状态机，不创建测试，也不选择具体任务运行时。后续 Rust API 应能表达这些约定，并在最小数据路径实现时检验是否足够简单。
