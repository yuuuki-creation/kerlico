# OpenVPN

协议 id 为 `openvpn`，客户端和服务端按各自的 `openvpn` feature 构建。支持 TCP 和 UDP 载体，默认 UDP。隧道使用 IPv4 TUN 的 `topology subnet`、双向证书校验、OpenVPN key method 2、TLS exporter 和 AES-256-GCM 的 `P_DATA_V2`。控制通道和数据帧格式以 [OpenVPN 协议说明](https://openvpn.github.io/openvpn/network_protocol.html) 为准。UDP 控制帧按序交付给 TLS，丢失时退避重发。数据帧在通过 AEAD 验证后才推进防重放窗口。

## 服务端

节点的 `protocol` 写 `openvpn`。以下字段放在节点的 `settings`。

| 字段 | 值 |
| --- | --- |
| `ca` | 验证客户端证书链的 CA，PEM 文本 |
| `certificate` | 服务端证书链，PEM 文本 |
| `privateKey` | 服务端私钥，PEM 文本 |
| `subnet` | 隧道网关及 IPv4 前缀，例如 `10.8.0.1/24` |
| `transport` | `udp` 或 `tcp` |
| `mtu` | 576 至 1500，默认 1400 |
| `users` | 每项包含 `email`、客户端证书的 DER SHA-256 十六进制字符串 `certificateSha256`，以及分配给该证书的单个 IPv4 `address` |

同一节点的账号、证书指纹和分配地址各自唯一。CA 验证通过后还须命中已登记的证书指纹。数据包的源地址须等于该账号的分配地址。移除账号会关闭当前会话。同一证书的成功重连会替换先前会话。认证后的 TCP、UDP 流由节点交给统一出站，照常使用节点规则和计数。OpenVPN 节点关闭隧道内 TCP 连接的 Nagle 算法，避免短控制消息等待上一段数据的确认。例如 UDP 反向压测可以更早收到启动消息并开始读取数据报。

UDP 的握手由有上限的工作线程完成。认证后由节点线程处理数据报，出口有数据时唤醒该线程。TCP 载体的工作线程也会在出口有数据时醒来。握手时向 TCP 载体的对端推送 `TCP_NODELAY`。Linux 用 epoll 等待套接字与出口事件。服务端连续两次套接字就绪的间隔少于 2 毫秒时，通常请求等待 50 微秒，以便一次读入同一突发中的后续报文。连续两次原生 UDP 请求提交后的载体就绪间隔少于 2 毫秒，且上一轮提交的最大批次少于 8 个请求时，请求等待 900 微秒。批次较大、已有原生 UDP 回复或收到显式唤醒时，直接处理这次原生 UDP 提交后的载体就绪。服务端每轮接收至多 32 个已就绪的 TCP 载体帧，并按同样上限发送数据帧。Linux 用批量套接字调用收发 UDP，已就绪的等长密文可以在内核分段。每个数据帧独立加密并检查序号，分段或批量调用不可用时仍按帧收发。

Linux 上，已选中原生出口的 UDP 流可以把出站连接好的套接字接入同一个就绪循环。节点按会话及套接字分发可读通知，出站持有套接字和双向计数。节点批量提交已解密的请求，对已就绪的回复重新封装为隧道数据包。只有原生 UDP 回复就绪时，若相邻两次此类就绪间隔少于 2 毫秒，且上一批收到了 1 至 7 个回复，读取前请求等待 900 微秒，以便合批。上一批较大或同时有载体输入或显式唤醒时，直接处理出口回复。非阻塞发送遇到临时背压时丢弃当前数据报。使用预读缓冲的流由统一出站复制，保留该缓冲的数据。

Linux 的 UDP 载体监听套接字和接入同一个就绪循环的原生 UDP 出口，在初始化时请求至多 512 KiB 的接收缓冲。请求受网络命名空间的 `rmem_max` 限制，现有更大的缓冲保留。内核报告的队列记账空间包含报文及其元数据。

## 客户端

客户端配置顶层使用 `protocol: "openvpn"` 和 `peer`。在 `settings` 里提供 `ca`、客户端证书链 `certificate`、`privateKey` 和服务端一致的 `transport`。可用 `serverName` 覆盖证书验证使用的名称，默认使用 `peer` 的主机名或 IP。独立客户端由出站模块拨载体。

Linux 和 macOS 使用 `kerlico-client --tun <接口名> <配置文件>`。客户端配置对端分配的地址、前缀和 MTU，目标网段的路由由调用方管理。服务端推送的路由和 DNS 不改动本机配置。库调用也可直接通过 `Client::start` 使用 `DataPlane`。

当前会话上限为一小时，结束后可以发起新连接。旧式密钥派生、压缩、密码认证、`tls-auth`、`tls-crypt` 和会话内重协商未实现。

## 验证

`tools/verify_openvpn.py` 以原版 OpenVPN 作独立对端，TCP、UDP 载体各跑两个方向。Linux 用临时网络命名空间和真实 TUN 设备核对 TCP 载荷、半关闭、UDP 载荷及来源，并拒绝由 CA 签发但没有登记的客户端证书。macOS 的原版对端用 PTY 接收和返回原始 IP 包，核对真正发送的数据帧，无需分配系统 TUN。

```text
cargo build --locked -p kerlico-client -p kerlico-server --no-default-features --features openvpn
sudo python3 tools/verify_openvpn.py --client target/debug/kerlico-client --server target/debug/kerlico-server --openvpn /path/to/openvpn --output /path/to/new-results
```

在 macOS 上，用以下命令构建包测试并取得输出里的可执行文件路径，将其作为 `--packet-probe` 传给同一验证脚本。以当前用户运行脚本。

```text
cargo test --locked -p kerlico-client --no-default-features --features openvpn --test openvpn_packets --no-run
```

2026-11-20 在 Linux 5.15 用原版 OpenVPN 2.6.12 跑通四组双向互通，在 macOS 26.5.1 用原版 2.6.23 跑通四组 UDP 载荷与来源验证。两端均通过 AEAD 篡改及防重放单测。

### 同带宽 CPU 对比

`tools/bench_openvpn.py` 在本机 Linux 的临时网络命名空间里跑同一个原版 OpenVPN 客户端和同一对 iperf3 探针，交替连接原版服务端及 Kerlico。两端使用 AES-256-GCM 和 1400 字节的 TUN MTU。原版关闭 DCO。对 TCP 载体的配对在客户端和两个服务端均启用 `TCP_NODELAY`。结果取服务端所有线程用户态与内核态 CPU 时间之和，除以应用接收端实际收到的数据量。每轮记录实际吞吐、重传或丢包，再计算配对的 CPU 降幅。带宽偏离目标或配对差异超过 2%，以及 UDP 丢包超过 0.1% 的组不用于计算降幅。

```text
cargo build --locked --release -p kerlico-server --no-default-features --features openvpn
sudo python3 tools/bench_openvpn.py --openvpn /path/to/openvpn --server target/release/kerlico-server --rate 100 --seconds 12 --rounds 4 --output /path/to/new-results
```

默认测 TCP 应用流量的上行和下行，覆盖 TCP、UDP 两种载体。加 `--payload udp` 可测 1200 字节的 UDP 应用数据报。Linux 压测机需要可用的 TUN、iperf3 以及 CPU 0 至 4。可用 `--iperf` 指定本地的 iperf3。支持 `--json-stream` 的版本可以用 `--warmup 2` 将开始的两秒从 CPU 和吞吐统计中同时排除。输出目录保存每轮的 JSON、进程日志和被测二进制的 SHA-256。UDP 载体和 UDP 应用测试都保存服务端及客户端各自网络命名空间的 UDP 套接字和计数。

再次将两个 Kerlico 构建与原版交替跑三轮 50 Mbit/s UDP 载体上行。当前构建唯一一轮有效配对的 CPU 比原版高 16.68%，与同轮上一构建的 CPU 时间同为 0.56 秒。另两轮分别因原版和当前构建的接收丢包而排除。当前构建被排除的那轮，内核在服务端网络命名空间记录 462 次 UDP 接收缓冲区溢出，其中 427 次出现在载体监听套接字。

同机隔离的回环 UDP 探针在开始读包前发送 120 个 1200 字节数据报，默认缓冲区接收了 93 个。请求 512 KiB 后，内核报告的实际缓冲区从 212,992 增至 425,984 字节，接收了全部 120 个。该探针只测套接字排队。

在 Linux 6.12 的真实 TUN 互通中，原版客户端以 50 Mbit/s 向 Kerlico 发送 UDP。三轮对照均在隧道建立后暂停监听线程约 24 至 27 毫秒。默认队列的监听套接字分别新增 285、38 和 41 次丢包，增大队列后三轮均为零。接收应用的丢包率由 0.127% 至 0.157% 降至 0% 至 0.038%。该测试测量暂停期间的排队能力。

同一负载暂停并恢复整个服务端进程时，只调整队列的构建会关闭 iperf3 的 TCP 控制连接。原生 TCP 出口对中断的读取重试后，两轮均保持连接并完成传输，UDP 应用接收零丢包。两项修复合并后，Linux 的真实 TUN 和 macOS 的 PTY 验证均通过四组原版互通。

Linux 5.15 的 18 秒诊断采样中，扩大队列前的构建在监听线程取得 408 个 CPU 样本。原生 UDP 提交到本地应用时的内核唤醒占监听线程样本的 16.42%，AES-GCM 解密占 6.13%，隧道内校验和占 1.72%。该轮开启了采样，用来定位开销。

调整监听队列并修复中断读取后，在 Linux 6.12 单 vCPU 上以 50 Mbit/s 复测两种载体的 UDP 应用流量。每轮预热 2 秒，采样 8 秒。TCP 载体下行有两轮超过丢包阈值，内核在 Kerlico 的原生 UDP 出口套接字上分别记录 778 和 69 次接收溢出。

| --- | --- | ---: | ---: |

| UDP | 下行 | 3 | 节省 13.33% |
| TCP | 上行 | 3 | 多用 5.88% |
| TCP | 下行 | 1 | 节省 11.66% |

在 UDP 载体上行试验中，原生出口对 2 至 8 个数据报改用 `sendmmsg` 的候选三轮均零丢包。它相对原版多用 17.09% CPU，同场的原实现多用 11.90%。保留原来的发送路径。

增大原生 UDP 出口的队列后，以同样的 50 Mbit/s 测试 TCP 载体下行。暂停处理该隧道的线程约 25 毫秒，默认队列三轮分别溢出 281、141 和 188 次，增大队列后分别溢出 139、0 和 0 次。无暂停的三轮复测中，Kerlico 接收端和原生出口队列均零丢包，应用交付 49.999 至 50.000 Mbit/s。原版有一轮超过丢包阈值，两轮有效配对的 CPU 降幅为 9.92% 和 37.12%，中位数为 23.52%。

Linux 6.12 上对 50 Mbit/s 的 UDP 载体上行做了约 1.1 秒的系统调用采样。监听线程的 5,387 次 `recvmmsg` 共读到 5,725 帧，其中 5,281 次只读到一帧，占 98.0%。同一窗口内调用了 5,389 次 epoll 等待和 5,280 次单包发送。采样用于区分每包开销和批量处理开销。

在 50 Mbit/s UDP 载体上行筛查中，对连续的原生 UDP 提交分别请求等待 250、500 和 900 微秒。250、500 微秒各有一轮因丢包超过 0.1% 而排除。900 微秒的两轮都有效，实际交付 49.967 至 49.995 Mbit/s，丢包率分别为 0% 和 0.060%。相对原版的 CPU 降幅分别为 25.49% 和 57.48%，中位数为 41.49%。

在两种载体各三轮的 900 微秒候选复测中，TCP 载体三轮均零丢包，CPU 降幅中位数为 37.32%，范围为 28.90% 至 66.00%。UDP 载体的三轮配对均因丢包排除，其中两轮是原版超过阈值，另一轮是候选超过阈值。该轮候选监听套接字新增 250 次溢出。
