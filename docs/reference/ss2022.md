# Shadowsocks 2022

协议 id 为 `ss2022`。客户端和入站使用 `ss2022` feature，落地使用 `landing-ss2022`。支持 [SIP022](https://shadowsocks.org/doc/sip022.html) 的 TCP 和 UDP 及 [SIP023](https://shadowsocks.org/doc/sip023.html) 的 AES 身份头。

| `method` | 每个密钥的字节数 | 多用户与中继 |
| --- | --- | --- |
| `2022-blake3-aes-128-gcm` | 16 | 支持 |
| `2022-blake3-aes-256-gcm` | 32 | 支持 |
| `2022-blake3-chacha20-poly1305` | 32 | 单用户 |
| `2022-blake3-chacha12-poly1305` | 32 | 单用户；Xray v26.10.31 和 Shadowsocks Rust v1.25.0 无此套件 |
| `2022-blake3-chacha8-poly1305` | 32 | 单用户；Xray v26.10.31 无此套件 |

三个 ChaCha 套件的 TCP 帧使用对应轮数的 ChaCha 和派生的会话密钥；UDP 使用对应轮数的 XChaCha，直接使用预共享密钥，每个报文携带 24 字节随机 nonce。

优先将随机生成的固定长度密钥编码为标准 Base64。为迁移 Xray 配置，解码时同样忽略 CR、LF 并接受末位未使用的填充位。无法解码时也接受长度正确的原始文本密钥。密钥不是一般用户口令。

客户端和落地的 `settings` 使用 `method`、`password`，以及可选的 `udp`（默认开启）。AES 多用户按 `身份密钥:用户密钥` 填 `password`。经过多跳中继时，从入口到目标依次填各跳的身份密钥和终点的用户密钥，用冒号分隔。独立客户端仍用共享 SOCKS5/HTTP 入口；落地使用服务端配置的 DNS 和 UDP/TCP 拨号。

TCP 首包可在本机应用发送数据之前发出，支持由目标先发数据的服务。没有应用载荷时按 SIP022 加入 1–900 字节的填充。客户端在固定响应头中校验回显的请求盐，匹配后才读取首个载荷。

TCP 写入先直接推进加密和发送；需要等套接字可写时，才由 Tokio 带超时继续同一次写入。已写出的密文不会重发。

服务端握手后，已绑定账号密钥和请求盐的发送状态与接收状态各持有一半套接字。上行继续读取握手留下的载荷，不与下行共用加解密状态的锁。透明中继也使用独立的套接字读写半边。

服务端在握手成功后预读密文，一次套接字读取可以涵盖多条记录；长度和载荷仍分别认证，未读完的数据保留到下一次读取。TCP 读取先直接尝试推进，只有需要等待套接字时才交给 Tokio 带超时继续同一次读取。写入及半关闭沿用独立的原路径。

已认证的 TCP 记录通过借用现有明文缓冲交给出口，出口写完后才消费，不先复制进通用转发缓冲。握手留下的载荷先交付；嗅探等普通读取与借用读取共享同一记录状态和消费位置。加解密及认证仍使用同一套 SIP022 状态机，半条记录可以跨读取超时继续，未通过认证的数据不会交出。透明中继不解密，沿用原读取方式。

接收端将认证完成的记录从原 `BytesMut` 存储切出，每批最多四条，不拼接或复制明文。下一条需要等待网络时立即交付已有记录；后续记录出错时先交付之前已认证的记录，再报告错误。普通读取、单段借用和向量借用共享消费位置。出口消费完一批后释放其存储引用，再复用有界的解密存储。

发送端把同一次应用写入中的至多四条记录直接封装进原密文缓冲，然后推进套接字写入。每条记录仍单独认证长度和载荷，保留 65,535 字节上限及原 nonce 顺序；不等待下一次应用写入凑批次。部分发送或等待可写时保留同一密文和对应的明文字节数，不重复加密。

原生异步出口可直接读取到这四条记录的载荷区域，再由同一 SIP022 编码器补入头部、原地加密并发送，省去通用缓冲到编码器的载荷复制。预留内存不提前生成响应时间戳或消耗 nonce；只封装本次实际读到的字节。存储初始化后保持尺寸并重复使用，不逐批清零或复制密文。普通写入也先填充相同区域，再调用同一封装和发送状态机。

TCP 入站选中原生出口时，将上述读写状态连同握手和嗅探剩余字节移交给统一出站，在已有 Tokio 执行器上持续转发，不再逐次将异步读写转成阻塞等待。透明中继同样移交其原始字节流。其他出口和同步调用使用同一状态机的同步接口；异步交接只能消费一次，交接后不再并行使用同步接口。转发的背压、计数、半关闭和共同空闲期限见服务端文档。

入站 `settings` 使用 `method`，并在 `users` 中为每个账号配置 `email` 和 `password`。未填 `identityKey` 时只接受一个用户；填 `identityKey` 后按用户密钥认证。可用 `mode` 选择 `tcp_only`、`udp_only` 或默认的 `tcp_and_udp`。

同一认证 UDP 会话的原生出口复用同一个本地 UDP 端口。通过 SS2022、WireGuard、Hy2、AnyTLS 或 mieru 落地时，同一会话的各目标共享一条落地 UDP 关联；WARP 在同一地址族的出口上也复用隧道内的源端口。回复携带数据报的实际来源；对端从另一个地址或端口回包时也可以返回该会话。透明中继只接受下一跳的回复。各目标仍按节点规则独立选出口。

入站 UDP 会话在上下行都空闲 300 秒后释放。通过认证和重放校验的客户端包、尺寸有效的出口回包都会续期；纯下行通信保留原会话、重放窗口和原生出站端口。这与 Xray 已建立的转发会话按双向活动续期的行为一致。

外层 UDP 载荷上限为 IPv4 的 65,507 字节或 IPv6 的 65,527 字节，包含加密封装。超过对应上限时只丢弃该数据报，会话仍可处理后续报文。实际路径的 MTU 仍可能限制能通过的尺寸。

收发两端的 UDP 重放窗口允许尚未接收、落后于最高编号至多 8,128 的报文，与 Xray 和 Shadowsocks Rust 一致。重复报文和更旧的报文不会到达目标。

客户端按 Xray v26.10.31 的规则保留当前和上一个服务端 UDP 会话。服务端重启后，同一客户端关联可以接收新会话的回包，也可以接收上一个会话迟到的合法包；每个会话独立防重放。上一个会话最后一次有效回包距今不足 60 秒时，不接纳第三个会话。无效或重复的包不会刷新这段时间。

通过 VLESS 落地时，同一认证 UDP 会话的目标共享 XUDP 或 Mux 会话；[独立 UDP 命令](vless.md)仍按目标打开。即使两条 SS2022 会话从同一个 UDP 套接字发出，它们的 VLESS 落地会话也互相隔离。

设置 `relay: true` 后，`identityKey` 必填，账号还要提供 `address` 和 `port`。该账号的 `password` 为下一跳的身份密钥（或单用户终点的密钥）。中继只剥掉一层身份头，通过节点分流将仍然加密的流量交给下一跳。回复由终点加密，中继原样转回。认证、时间戳和重放保护仍由终点执行；中继另按用户与 UDP 会话隔离转发状态。

本机互通脚本为 `tools/verify_ss2022.py`，对照 Xray v26.10.31 和 Shadowsocks Rust v1.25.0。夹具覆盖 TCP、HTTP CONNECT、UDP、AES 多用户、透明中继及 UDP 源端口复用。两跳中继分别验证 Kerlico → Xray 和 Xray → Kerlico 的顺序，AES-128 与 AES-256 都覆盖。用开启 `aead-cipher-2022-extra` 的 Shadowsocks Rust 对照 ChaCha8。`--hysteria`、`--mihomo` 和 `--mita` 分别用官方 Hy2、mihomo AnyTLS 和原版 mita 验证落地的 UDP 源端口和回包来源。后两项也以 Kerlico 服务端作对端；mieru 分别验证 TCP 和 UDP 底层传输。

`--vless-peer` 用 Xray 和 Kerlico 分别检查独立 XUDP 与 Mux 落地，也验证从同一外层 UDP 套接字发出的两条 SS2022 会话保持隔离。

`tools/verify_ss2022_chacha.py` 是独立线协议夹具，双向验收三个 ChaCha 套件的 TCP 和 UDP，也验证 ChaCha12 经落地时两目标仍共享 UDP 会话。传 `--reference` 可先用启用 ChaCha8 的原版 Shadowsocks Rust 验证夹具本身。

`--udp-size` 验证两个外层地址族的最大报文、超限后的会话连续性和完整数据。Linux 上对照原版时，在隔离网络命名空间把回环 MTU 设为至少 65,575 字节，使 IPv6 最大报文能在不依赖分片的情况下通过；隔离环境内为原生出口准备 IPv4 路由。

`--udp-window --xray ... --reference ...` 对照两个原版，确认窗口边界、拒绝重复，以及丢弃旧包后仍能处理后续数据。

`--udp-sessions --xray ...` 对照 Xray 验证服务端重启后的客户端会话切换，以及客户端更换外层源端口后，原生出站端口、回复会话和重放窗口都保持不变。`--tcp-salt --xray ...` 验证客户端在对端只送来错误盐的固定响应头时就拒绝连接。

`--udp-downlink-idle 315 --xray ...` 只发送一个客户端包，随后由源站持续回包超过五分钟，对照 Xray 验证同一会话和响应序号在纯下行期间持续有效。

## 固定 500 Mbps 对照

2026-11-18 在 perf-01 的隔离 veth 内网比较 Kerlico 和 shadowsocks-rust。两个服务端使用同一客户端和 8 条持久 TCP 流，固定服务端核 1–2。每轮预热 5 秒、计量 30 秒，核对 1,875,000,000 字节，速率误差小于 1%，最大发送迟到小于 1 秒。双方使用 2022-blake3-aes-128-gcm，官方服务端启用 TCP_NODELAY。上行首组服务端进程 CPU 降低 15.79%，下行首组降低 7.08%，两个方向均在第一个有效配对后依规则停止，未达到 31%。

Kerlico 服务端 SHA-256 为 `13ae6e69bcc9ade8f7cccecc4cff18f07a0f538fbc3e34a05e59a4d7a3abdcaf`，shadowsocks-rust 为 `0140c770c2d70c5c446b6e16fe2cb52f8decf978a81a30c1a841140c1abfb6a4`，共同客户端为 `22bdea591247fed9ec049e75f2461c61fbe9b144152a16ee940ea9d153b37c2a`。
