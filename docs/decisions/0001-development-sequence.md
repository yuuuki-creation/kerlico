# 0001 先搭框架，再逐个协议，按开发需要调研

状态：已取代。原确认日期：2026-10-30。当前流程见 [0002](0002-support-catalog-before-implementation.md)；框架先行与逐项实现仍保留，支持目录已按用户最新要求提前调研。

## 问题与用户要求

项目需要保持模块独立、便于增加协议，同时避免在真正开发前提前消耗精力研究全部协议。用户明确要求先规划支持范围，之后先搭框架，再一个协议一个协议接入；相关协议的调研在开发时才进行。

## 采用的流程

先形成支持清单与优先级草案。获得开始实现的明确指令后，先完成最小框架及其验收，再按当前排期一次研究、实现和验证一个协议。

具体协议的规范、固定源码、版本、算法、传输/安全组合与依赖选型在该模块开发时研究。必要的关联能力可以随当前任务研究，不预先扩展为下一批协议调研。已有整体架构研究保留，不删除历史资料。

用户进一步明确：每个协议开工前，必须详细调研当前任务涉及的传输、安全、flow/复用及合法组合、依赖和测试要求。支持与验证按具体组合记录，不能只凭协议名称宣称覆盖全部变体。现在只固定这项规则，不提前展开详细矩阵。

当前任务完成既定验收并更新状态后，才进入下一个协议。框架契约允许随着真实接入需求演进，不以提前穷举协议能力换取表面的接口稳定。

## 取舍

相较提前调研全部协议，此流程把研究与实际决策放在同一阶段，减少资料过期和空泛抽象；代价是后续协议可能揭示公共接口需要调整。调整时保留变更理由和已有协议的验证，不能为了不改接口而隐藏特殊分支。

相较同时开发多个协议，此流程便于把错误定位到当前模块并验证扩展入口；代价是不能同时宣称大范围协议覆盖。阶段能力以实际交付记录为准。
