# 0010 节点出站模式、设备共享WARP与远端透传

状态：节点模式、双栈缺族补齐和远端透传责任由用户明确确认；配置字段、WARP接入和内部类型仍为设计建议，尚未实现或验证。日期：2026-11-01。

## 用户确认与取代范围

用户明确：部署一个节点时指定`v4 only`、`v6 only`或双栈。双栈缺少其中一种原生出站能力时自动配备CF WARP；一台设备统一配置WARP的IPv4、IPv6出站，通过共享调度核心调度。分流给远端代理的请求保留原样，远端执行自己的目标策略，失败不由本节点改换网站地址或出口补救。

本记录保留[0009](0009-global-egress-dispatcher.md)的唯一共享调度器、命名出站表和多远端规模，修正其关于远端代理路径也由本机解析并选择网站IP的建议。调度器先区分本节点负责目标策略的出网路径和远端透传路径，不能先统一改写所有业务目标再决定去向。

## 两条数据路径

本节点负责的出网路径包括原生网络和由本设备管理的WARP出口。该路径应用节点地址族模式，解析网站目标并选择所需地址族的设备出口。

远端代理路径保留原始业务目标的域名或IP、端口和业务负载，按选定代理协议编码后转交。这里的原样指请求语义和负载，不是复制入站的认证材料或加密帧。网站解析、IPv4/IPv6选择及后续连接策略由远端代理负责，本机不将网站域名先改成IP，也不套用本节点的网站地址族模式。

代理端点自身的地址解析和载体拨号仍由本地完成，与被代理的网站目标分开。比如本节点的本地目标模式为IPv6 only，并不据此改写远端网站目标；代理载体使用哪一族仍是独立的连接配置。

## 节点模式

以下名称是设计概念，不是当前JSON v1已接受的字段。

| 节点模式 | 本节点负责路径的目标地址选择 |
| --- | --- |
| IPv4 only | 只使用IPv4目标和设备IPv4出口，不回退为IPv6目标 |
| IPv6 only | 只使用IPv6目标和设备IPv6出口，不回退为IPv4目标 |
| 双栈 | 两族目标均可用，延续默认IPv4优先；缺少的原生出站族由设备共享WARP补齐 |

字面IP保持原地址。若与本地路径的单栈模式不兼容，明确拒绝，不把它隐式转换成另一族。双栈的具体候选等待与建立阶段回退方式仍需实现设计；已交付业务数据不重放，UDP不因收包超时换族重发。

## 设备共享出口

建议设备级出口注册表提供`Native4`、`Native6`、`Warp4`和`Warp6`四类逻辑能力。`Warp4`和`Warp6`复用同一套设备WARP运行环境，不是每节点各装一套WARP。各节点和运行实例取得共享出口引用，不能独立维护或反复注册同一设备资源。

| 设备原生能力 | 双栈节点的出网组合 |
| --- | --- |
| IPv4及IPv6均可用 | Native4与Native6 |
| 仅IPv4可用 | Native4与Warp6 |
| 仅IPv6可用 | Warp4与Native6 |

部署准备阶段在设备级确保缺失能力，准备成功后再向调度器发布。不能因为存在本地IPv6地址、WARP接口或代理端口就登记出网可用，也不能在补齐失败时将双栈节点静默降为单栈。单个网站连接失败不等于设备缺族，不因此反复安装或重配WARP。

自动补齐的明确确认范围是双栈缺族；单栈缺少对应原生能力时是否也自动创建WARP，尚未另行确认。单栈可以使用设备注册表已有的对应族出口，但不能据此增加新的自动部署承诺。

WARP环境由设备级所有者管理生命周期。单节点或Engine退出只回收自己的会话、连接与引用，不关闭其他节点正在共用的WARP服务。部署资源准备与配置纯校验分开；`Registry::prepare`和CLI `check`不得因此变为安装软件或修改系统网络的入口。

具体WARP接入方式尚未选择，必须验证既定TCP、固定UDP、多目标关联及目标地址族语义。Cloudflare的[客户端模式](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/configure/modes/)区分IP隧道与Local proxy模式，不能仅凭一个本地SOCKS/HTTP入口声明已满足本项目全部数据能力。

## 远端透传与失败

远端可以有多个独立代理。调度器按配置先选定代理或初始出站组成员，再把原请求交给它；该请求后续的网站目标策略归远端，不因远端失败在本节点自动换网站地址族、换代理、换成原生直连或WARP重试。出站组若保留，只用于本次初始选择，不自动包含故障切换。

错误仍须按协议返回，或结束会话并释放本地限额与资源。远端失败不改变本节点的地址族模式，也不影响无关节点和请求。多目标UDP关联保持代理、来源和包边界，不由本机给远端路径重新选择网站IP；不支持保留原目标类型的协议组合明确拒绝，不悄悄本地解析替代。

Xray非Freedom出站的[`targetStrategy: AsIs`](https://xtls.github.io/config/outbound.html)可作为保留目标域名交远端处理的参考。节点三种模式和设备级自动WARP补齐是本项目要求，不登记为Xray提供的同名能力。

## 影响与当前状态

配置需要表达节点目标模式和本地/远端出站绑定；共享调度器需要在任何网站目标改写前确定责任分支。原生与WARP后端由设备资源层共享，代理协议出站保持原目标；回包仍回原节点。

当前Egress会对代理出站的网站域名执行本地解析，尚不满足透传要求；节点三种模式、设备出口注册、WARP准备和共享调度器也未完成。目标流量图与地址规则统一维护在[节点与统一出站](../node-egress.md)。后续应验证缺族补齐一次、多节点共享、单栈限制、远端保留目标、失败不触发本地替代，以及TCP/UDP回包与取消归属。

本轮仅更新架构约定与设计，不安装或配置WARP，不连接机器，不修改运行源码，不新增构建、测试或发布结果。既有代码停点和未验证项仍由根STATUS维护。
